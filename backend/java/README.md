# Resident CQL worker (stage 1)

Run `./run-worker.sh`; stdin and stdout are serial NDJSON. Startup compiles the Java modules into `java/build` using an operator-provided JDK 21 and official CQL jar. Configure `CQL_JAR` and `CQL_JAVA_HOME` (or `JAVA_HOME`) in the project’s ignored `.local/cql.env`; see the backend README. CQL console output is redirected to stderr. Every operation constructs fresh official parser, typing, and evaluation environments; no user CQL, Java, SQL, paths, or options are accepted.

Wire request: `{"id":"r1","op":"schema_validate","payload":{"schema":{...}}}`. Operations: health; schema_validate; draft; validate. The latter two take `source`, `target`, and optional `assignments` (or `recipe.assignments`). Response: `{id,ok,result}` or `{id,ok:false,error}`. A successful protocol response may contain a validation `status` of valid, incomplete, invalid, or inconclusive. Unsupported subsets return inconclusive + unsupported diagnostic.

Schemas use the frontend's exact native `SchemaSpec`: tables/columns/primaryKey/uniqueKeys, foreign_keys, and equations. Native names remain metadata and IDs map to compiler-generated CQL symbols. dataType accepts text, integer, real, boolean. Generated identities and storage reference carriers remain in the lossless native manifest but are excluded from CQL scalar attributes. Nongenerated identity columns remain explicit scalar attributes, including business primary keys; their draft scalar holes carry role `identity`. Physical foreign-key binding equations are emitted only when both scalar carriers are visible. Primary/unique keys and nullable are retained as metadata: stage 1 does not claim to enforce database uniqueness or implement null instance semantics.

Supported native equations are variable/unary attribute/reference paths. Constants explicitly return unsupported. Supported query DTO is the existing unannotated raw_term subset: variable/unary paths, FROM bindings, WHERE equations, attribute terms, and FK block substitutions. Hole IDs use native target IDs (`Entity.from`, `Entity.attribute.column`, `Entity.foreignKey.fk`). Do not insert compiler symbols into DTOs. Query results are validated by official CQL and contain program source + SHA-256. Draft skeleton placeholders are display source and are never claimed to have evaluated successfully.

`python3 smoke.py` tests schema validation, incomplete skeleton, a complete two-entity query, wrong scalar/entity type, and missing foreign-key substitution using the real resident worker. It writes an ignored local `smoke-results.json`. Execution support is documented below; frontend Apply is owned by its separate lane.

## Execution stage

`evaluate` now accepts the same source/target/assignments and `data:{tables:{nativeTableID:[{nativeColumnID:cell,...}]}}`. It builds a fresh official literal instance and evaluates the query. Every source table requires a declared native primary key; all physical scalar cells must be present, including hidden identities/references. Duplicate PKs, ambiguous/unresolved FKs, Int64 overflow, and malformed scalars are rejected. Nulls are explicitly unsupported. Text, Int64 and exact decimal values enter as JSON strings; Boolean accepts JSON bool or canonical `true`/`false` strings. Outputs include target-native table/column/FK IDs, row IDs, resolved FK row IDs, targetSchema verification metadata, input PK→generator manifest, timings, and program digest. The request target is authoritative; returned targetSchema never proposes a replacement. Supplied targetHash/baseRevision/sourceDataDigest are echoed, with canonical hash validation owned by the Rust run boundary.

`evaluate-smoke.py` covers real small instance execution and FK/null negatives. `typed-smoke.py` checks Int64 maximum, exact decimal trailing precision, bools, overflow, and malformed bools.

`evaluate_recipe` is the explicitly bounded server recipe `evan.factor_entities.v1`, not a generic migration compiler. It requires source/target/data and explicit six-map bindings: sourceEntities/sourceAttributes/sourceForeignKeys/targetEntities/targetAttributes/targetForeignKeys. Map keys are bundled role symbols, values are authoritative native IDs. Source role bindings may read a hidden physical key as a business recipe input; this does not expose that key as a general schema business arrow. Target coverage, scalar sorts, and FK destinations must match the selected native schema. The four recipe definition assets have SHA-256 checks and contain no input rows. Execution materializes a fresh normalization result, bridges it in memory into the String-valued post-typing input, executes the typed query and seven official checks, and emits fresh native-ID output. No stored Result.json or TypedResult.json is read. The original experiment also included a full Evan regression; its CSV inputs and run artifacts are intentionally not bundled here.

The successful first full regression materialized 500 Ticket, 821 Market, 1178 Coupon, 182 Airport and 49 State rows in 126.9 seconds, including seven executed official check commands. The original experiment recorded digests and timings. Its run predated restoration of the fixed `interpret_as_algebra` Input performance option; no second full execution was performed. Bundled recipes currently reject additional native `equations` rather than silently omitting constraints not represented by the pinned recipe. Generic query execution supports the native path-equation subset.

Business-key transport: the pinned Evan recipe may bind an existing official scalar role through `targetAttributes` to a hidden `storage: "identity"` primary-key column with no `generated` marker. All ordinary target attributes and all nongenerated target PK components must be explicitly covered. These bound values are emitted in output `values` under native column IDs, using the same exact scalar conversion as other attributes. A hidden reference carrier or generated identity cannot be bound as an official scalar role. The generic compiler requires an explicit scalar assignment for each nongenerated business PK, including `storage: "identity"` columns; an absent assignment leaves validation incomplete. It does not guess a source identity or invent keys. Generated identity columns retain their existing client materialization behavior.

`KeyTransportSmoke.java` is a small query regression and pinned recipe schema-only preflight (no Evan rows or full recipe execution), checking text `0012`, maximum signed Int64, explicit business key holes, and generated-key compatibility. The optional `--evan-preflight` requires an operator-supplied `evan-smoke-request.json` and only checks recipe schemas. Compile after `run-worker.sh </dev/null` into `build` with classpath `build:$CQL_JAR`, then run with `-Dcql.recipe.dir=recipes` and the same classpath.
